# djangoer-examples

The models of well-known Django projects, written out by
[Djangoer](https://github.com/nakita628/djangoer): the ER diagram as Mermaid, SVG and DBML, and
the Markdown docs of every model. Beside them, in `models/`, is the Python they are drawn from.

## How

The tutorials, the domains and the Django features are samples whose `models.py` is in this
repository: they are written without `--all`, as a project's own models, and cover what the
projects above do not use.

Each directory of `examples/` installs the project and Djangoer (`pyproject.toml`, with
[uv](https://docs.astral.sh/uv/)) and a `settings.py` that installs the project's apps. The
projects are installed from PyPI, so their models are not the project's own to Djangoer: the
examples are written with `--all`, which also covers the models of Django and of the packages
each project uses.

`models/` holds the source of every model on the diagram: the file that defines it, and the files
of the abstract models it inherits its fields from, at their path in the installed package
(`models/wagtail/models/pages.py`). They are copied as they are, under the license of the project
they come from.

### Layout

```
pyproject.toml       this app's tooling (ruff), Python 3.14 in .python-version
scripts/             readme.py, new_example.py, new_sample.py, collect_models.py
tools/               the Bazel macro (defs.bzl) and the runner of one example (run.py)
examples/<name>/     one standalone uv project per example: pyproject.toml, uv.lock, settings.py,
                     BUILD.bazel, and what Djangoer writes (er.md, er.svg, schema.dbml, docs/, models/)
```

The examples are not a uv workspace: each installs a different project with its own Django and
dependencies, which cannot share one lockfile, so each keeps its own `uv.lock`.

### Usage

[Bazel](https://bazel.build/) through bazelisk, from the root of the repository. uv is pinned in
`MODULE.bazel`, and it installs Python 3.14 and each example's locked environment (into
`~/.cache/orm-generators-examples/djangoer`, or `$DJANGOER_CACHE`). The environments come from
PyPI, so these targets run outside the sandbox, and the tests are tagged `djangoer`, which
`bazel test //...` leaves out.

```bash
# Run Djangoer on every example and compare with the committed output; also ruff and README.md
bazel test --config=djangoer //apps/djangoer/...

# Only one
bazel test --config=djangoer //apps/djangoer/examples/wagtail:generate.test

# Rewrite one example's output
bazel run //apps/djangoer/examples/wagtail:generate.write

# The list above, from readme.py's GROUPS
uv run --project apps/djangoer apps/djangoer/scripts/readme.py

# A new example (or a sample: scripts/new_sample.py NAME app1,app2, then write its models.py)
uv run --project apps/djangoer apps/djangoer/scripts/new_example.py NAME "dep1,dep2" "app1,app2"
```

`uv run --locked` refuses an example whose `uv.lock` is out of step with its `pyproject.toml`: run
`uv lock --project apps/djangoer/examples/<name>` after changing it.

Djangoer is installed from PyPI (`djangoer>=0.5.0`).
